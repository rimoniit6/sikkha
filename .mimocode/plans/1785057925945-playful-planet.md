# Board Question (বোর্ড প্রশ্ন) System — Complete Audit Report

---

## 1. Current Hierarchy

The system uses a **flat string-based hierarchy** with foreign keys only at the Chapter level:

```
ClassCategory (id, slug)
   ↓ (1:N)
Subject (id, classId → ClassCategory.id)
   ↓ (1:N)
Chapter (id, subjectId → Subject.id)
   ↓ (1:N)
MCQ / CQ
   ├── chapterId → Chapter.id (FOREIGN KEY with CASCADE)
   ├── classLevel: String (slug, e.g. "ssc") — NO FOREIGN KEY
   ├── subjectId: String (ID, e.g. "clx...") — NO FOREIGN KEY
   ├── board: String? (slug, e.g. "dhaka") — NO FOREIGN KEY
   └── year: String? (e.g. "2024") — NO FOREIGN KEY

Board (id, name, slug) — separate model, NO FK from MCQ/CQ
ExamYear (id, year) — separate model, NO FK from MCQ/CQ
BoardYear (board slug, year) — junction, NO FK from MCQ/CQ
```

**Critical observation:** `classLevel`, `subjectId`, `board`, and `year` on MCQ/CQ are **denormalized strings** — they have NO foreign key constraints to their respective models. Only `chapterId` has a proper FK with CASCADE.

## 5. Problems Found

### CRITICAL

#### C1 — Type Case Mismatch Breaks Board MCQ Creation
**File:** `src/app/api/admin/board-questions/route.ts:204`
**Root Cause:** The Zod schema validates `type: z.literal('mcq')` (lowercase) at line 12, but the POST handler checks `if (type === 'MCQ')` (uppercase) at line 204. The admin form sends `type: 'mcq'` (lowercase) at `AdminBoardPage.tsx:309`.
**Flow Trace:**
1. Admin form submits `{ type: 'mcq', question: '...', ... }`
2. Zod validates against `createBoardMcqSchema` — `type: z.literal('mcq')` ✅ passes
3. Handler destructures `const { type } = body` → `type = 'mcq'`
4. `if (type === 'MCQ')` → FALSE (lowercase ≠ uppercase)
5. Falls through to line 230: CQ schema validation
6. CQ schema expects `uddeepok`, `question1`, `answer1` — MCQ body doesn't have these
7. Returns 400 validation error
**Impact:** Board MCQ creation from the admin page is completely broken. Only CQ creation works.
**Fix:** Change line 204 from `if (type === 'MCQ')` to `if (type === 'mcq')`.

#### C2 — Unbounded findMany Loads Entire Database into Memory
**File:** `src/app/api/admin/board-questions/route.ts:168-176`
**Root Cause:** When `type` parameter is null/undefined (the default admin list view with no type filter), the code at lines 171-173 executes:
```ts
db.mCQ.findMany({ where: mcqWhere, include: { chapter: chapterInclude }, orderBy: { createdAt: 'desc' } })
db.cQ.findMany({ where: cqWhere, include: { chapter: chapterInclude }, orderBy: { createdAt: 'desc' } })
```
No `skip` or `take` is applied. The `page` and `limit` variables from lines 124-125 are only used for the final `.slice()` at line 184-185, not for the database queries.
**Impact:** With 10,000+ MCQs and 5,000+ CQs, this loads 15,000+ records with full chapter includes into Node.js memory per request. Causes OOM crashes and extreme slowness.
**Fix:** Apply `skip` and `take` to both `findMany` calls, similar to how the MCQ-only and CQ-only branches handle it.

### HIGH

#### H1 — No Foreign Keys on board, year, classLevel, subjectId
**File:** `prisma/schema.prisma:264-352`
**Detail:** The MCQ and CQ models store `board` (string slug), `year` (string), `classLevel` (string slug), and `subjectId` (string ID) as plain strings. The `Board`, `ExamYear`, `Subject`, and `ClassCategory` models all exist in the schema but have NO foreign key relationship to MCQ/CQ.
**Consequences:**
- Deleting a Board leaves orphaned `board` strings in MCQ/CQ
- Renaming a Board slug breaks all queries using that slug
- No cascade deletes — soft-deleting a Subject doesn't affect MCQ/CQ records
- Invalid board/year values can be inserted (e.g., `board: "nonexistent"`)
- `BoardYear` junction table exists but is never referenced by MCQ/CQ

#### H2 — N+1 Query Pattern in Filters API
**File:** `src/app/api/board-questions/filters/route.ts:88-94`
**Detail:** For each unique `classLevelSlug`, the code runs:
```ts
const [mcqCount, cqCount] = await Promise.all([
  db.mCQ.count({ where: { ...mcqWhere, classLevel: cls } }),
  db.cQ.count({ where: { ...cqWhere, classLevel: cls } }),
])
```
With 5 class levels (Class 6, 7, 8, SSC, HSC), this executes 10 additional count queries on every filter request.

#### H3 — `unlocked` Filter Behaves Identically to `free`
**File:** `src/app/api/board-questions/route.ts:120-124`
**Detail:** The access filter logic:
```ts
access === 'free' ? { isPremium: false }
  : access === 'premium' ? { isPremium: true }
  : access === 'unlocked' ? { isPremium: false }  // ← SAME as 'free'
  : undefined
```
Users who purchased premium content and expect to see "unlocked" items see the same results as "free" — their purchased content is not distinguished.

#### H4 — Type Case Mismatch in TypeScript Types
**File:** `src/components/admin/board/types.ts:24`
**Detail:** `FormState.type` is typed as `'mcq' | 'cq'` (lowercase), matching the form behavior. But the API POST handler checks for `'MCQ'` (uppercase). This is the client-side manifestation of C1 — the type system and API contract disagree on casing.

## 10. Recommended Architecture

### Current (Denormalized)
```
MCQ/CQ
  ├── chapterId → Chapter.id (FK) ✅
  ├── classLevel: "ssc" (string, no FK) ❌
  ├── subjectId: "clx..." (string, no FK) ❌
  ├── board: "dhaka" (string, no FK) ❌
  └── year: "2024" (string, no FK) ❌
```

### Recommended (Normalized with Auto-population)
```
MCQ/CQ
  ├── chapterId → Chapter.id (FK) ✅ keep
  ├── classLevel → ClassCategory.slug (add FK or validate against ClassCategory) 
  ├── subjectId → Subject.id (add FK constraint)
  ├── board → Board.slug (add FK constraint)
  ├── year → ExamYear.year (add FK constraint)
  └── Add: examType (optional, for exam categorization)
```

### Upload Flow Improvement
```
Admin selects: Class → Subject → Chapter (existing cascade ✅)
Admin selects: Board (dropdown, already exists)
Admin selects: Year (dropdown from ExamYear, not free text)
  ↓
System auto-derives:
  - classLevel from classId → ClassCategory.slug
  - subjectId from the selected Subject
  - board from the selected Board slug
  - year from the selected ExamYear
  ↓
Admin enters only:
  - Content (question text, options, answers)
  - Topic (optional)
  - Difficulty
  - Premium status
```

### Key Changes
1. **Add FK constraints** for board, year, subjectId on MCQ/CQ
2. **Change year from free text to dropdown** from ExamYear model
3. **Fix type case mismatch** in POST handler (use lowercase everywhere)
4. **Add pagination to admin GET** when no type filter
5. **Auto-fill board/year** from last-used values or class-level defaults
6. **Add duplicate detection** before insert
7. **Implement proper access control** for `unlocked` filter
